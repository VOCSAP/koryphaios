## 1. Problème et périmètre

Chaque session Claude Code lance deux processus bun, `server.ts` (claude-peers) et `server-roadmap.ts` (kory-roadmap). Cible : un daemon bun par utilisateur OS, par machine et par racine de code (§6.2), et par session deux relais Rust (`--family peers`, `--family roadmap`) qui copient le JSON-RPC MCP entre Claude Code et le daemon.

Décisions déjà tranchées par l'opérateur, non rouvertes ici : daemon local dédié, un seul daemon pour les deux familles, les deux familles par le même relais stdio, relais en Rust, repli vers les serveurs bun si le binaire manque, scénario obligatoire de sessions Kory et hors Kory ensemble. Elles sont consignées dans l'ADR 008 avec les options écartées.

**Non-objectifs de ce chantier.** Les tuiles sandbox restent sur `server.ts` dans le conteneur. `kory-deck` et `kory-operator` (servis par `server-deck.ts` et les scripts de `desktop/mcp/`) restent des processus Kory distincts. Aucun changement du protocole WebSocket du broker : une WebSocket par session.

**Ce qui ne doit pas casser.** Une tuile Kory n'entre jamais dans le groupe par défaut de l'utilisateur. Deux tuiles dans le même dossier gardent chacune leur identité. Le broker voit mourir une session quand elle meurt. La roadmap refuse fermé sans identité prouvée. Les approbations restent locales au run Kory.

**DÉCISION, fichiers cibles.** Crate Rust `relay/` à la racine du dépôt, binaire `claude-peers-relay`. Point d'entrée du daemon `mcp-daemon.ts` à la racine, frère de `server.ts`. Logique de session dans des modules sans effet de bord à l'import : `shared/peers-session.ts` (fabrique de la famille peers, handlers et gestionnaires d'outils exportés vers `server-deck.ts`) et `shared/roadmap-session.ts` (autour de `shared/roadmap-mcp.ts`). Protocole commun : `shared/mcp-daemon-protocol.ts` (trames, validation du hello, MAC) et fixtures partagées `relay/protocol-fixtures/`. **DÉCISION, un seul chemin de code.** `server.ts` et `server-roadmap.ts` deviennent des entrées stdio minces : elles construisent un hello depuis `process.env`, `process.cwd()`, `process.pid` et `process.ppid`, puis appellent la même fabrique que le daemon. Le repli bun et le daemon exécutent donc le même code de session. Écarté : garder `server.ts` intact à côté d'un nouveau code multi-session, ce qui créerait deux implémentations qui divergent dès le premier correctif.

## 4. Protocole entre relais et daemon

### 4.1 Transport

**DÉCISION : TCP sur `127.0.0.1` sur les trois plateformes, avec authentification mutuelle applicative (§5).** Écarté : pipe nommé sous Windows et socket unix ailleurs. Raisons : deux codes de transport à tester ; sous Windows, la sécurité d'un pipe tient à son descripteur de sécurité, que libuv ne permet pas de fixer.

**MESURÉ documentaire**, `mcp__crawl4ai-rag__searxng_search("node net.createServer named pipe security descriptor DACL windows not supported")`, issue nodejs/node#47086 : « Node (well, libuv) calls CreateNamedPipe () with the WRITE_DAC (but not WRITE_OWNER) flag and default security attributes ». **SUPPOSÉ** : le serveur de pipe de Bun sous Windows a la même limite ; non vérifié. Un socket unix dans un dossier `0700` serait sûr sous Linux et macOS, mais l'authentification applicative reste nécessaire pour Windows : un seul mécanisme partout coûte moins qu'un mécanisme par OS.

**Ports candidats (Q1, DÉCIDÉ).** Port de base `p0 = 47000 + (fnv1a32(nom d'utilisateur en minuscules) mod 1000)`, puis les 9 suivants : 10 candidats, même règle sur les trois OS. `CLAUDE_PEERS_MCP_DAEMON_PORT`, s'il est défini dans l'environnement du relais, remplace la liste par ce seul port. Le port reste le verrou : un daemon par port, et le plus bas gagne (§6.2). Un candidat tenu par un autre programme, par le daemon d'un autre compte ou par le daemon d'une autre racine de code est sauté : l'authentification ou le hello échoue, jamais avec une fuite. Tous les candidats occupés sans daemon valide : repli (§10), journalisé. Écarté : port fixe unique, qui bloque le second compte d'une machine partagée ; port unique dérivé sans candidats, qui force le repli à la première collision ; port choisi par l'OS et publié dans un fichier, qui obligerait à un verrou de fichier propre à chaque OS.

### 4.2 Trames

**DÉCISION.** Chaque trame avant `AUTH_OK` : longueur `u32` little-endian, un octet de type, puis une charge UTF-8 ; la longueur compte l'octet de type et la charge. Charge maximale 16 Mio ; avant que le pair ait prouvé la clé (`CHALLENGE`, `AUTH_OK`) et pour `WELCOME`, 64 Kio. Une longueur nulle ou une charge au-dessus de la limite est une violation de protocole et ferme la connexion avant la lecture du corps. **Après `AUTH_OK`, toutes les trames, `HELLO` et `ERROR` compris, sont scellées** (§4.3) : `u32le L || C || tag`, avec `C = AES-256-GCM(type || charge)`, un `tag` de 16 octets et `L = 1 + taille de la charge + 16` (au moins 17, au plus 16 Mio + 17). L'AAD est formée des 4 octets de `L`. Le nonce de 12 octets est formé de 4 octets nuls puis du compteur de trames du sens (u64 big-endian, depuis 0, plus 1 par trame, arrêt à 2^48). Un tag invalide, une longueur hors limites ou un compteur épuisé ferme la connexion tout de suite, sans trame `ERROR`, avec une ligne de log. La fixture `relay/protocol-fixtures/frames.json` porte les numéros de type, les limites, un exemple de trame en clair et quatre trames scellées dont une de chaque sens au compteur 1, calculés par bun. Écarté : NDJSON avec un préfixe de méthode réservé, qui mélange le contrôle et le MCP dans le même espace de noms.

| Type | Sens | Charge |
|---|---|---|
| `0x01 CHALLENGE` | daemon vers relais | JSON `{proto_min, proto_max, daemon_nonce, daemon_instance, daemon_version}` |
| `0x02 AUTH` | relais vers daemon | JSON `{proto_min, proto_max, relay_nonce, mac}` |
| `0x03 AUTH_OK` | daemon vers relais | JSON `{proto, mac}` |
| `0x04 HELLO` | relais vers daemon | JSON, §4.4 |
| `0x05 WELCOME` | daemon vers relais | JSON `{session_id, family, tools_hash, resumed}` |
| `0x10 MCP` | les deux sens | exactement un message JSON-RPC, sans saut de ligne final |
| `0x11 TICKET` | daemon vers relais | JSON `{ticket}` |
| `0x12 BYE` | relais vers daemon | JSON `{reason: "stdin_eof" \| "signal"}` |
| `0x13 PING` / `0x14 PONG` | relais vers daemon / retour | vide |
| `0x15 ERROR` | daemon vers relais, avant fermeture | JSON `{code, message}` |
| `0x20 CONTROL` | client CLI ou daemon vers daemon, à la place de HELLO | JSON `{op: "status" \| "stop"}` ; `status` répond `{pid, pid_start, port, code_root, code_fingerprint, version, sessions}` |

Codes d'`ERROR` : `proto_mismatch`, `hello_invalid`, `root_mismatch` (le relais essaie le candidat suivant, §6.2), `family_unavailable`, `session_limit`, `ticket_refused` (non fatal, voir §4.6), `control_invalid` (opération `CONTROL` inconnue, ou daemon sans gestionnaire pour cette opération), `shutting_down`.

### 4.3 Poignée de main

1. Le daemon envoie `CHALLENGE` avec un `daemon_nonce` de 32 octets aléatoires (base64url).
2. Le relais répond `AUTH` : `relay_nonce` de 32 octets (base64url) et `mac = HMAC-SHA256(clé, "kory-mcp-v1|relay|" + daemon_nonce + "|" + relay_nonce + "|" + hC + "|" + proto_min + "|" + proto_max)`, où `hC` est le base64url du SHA-256 des octets bruts de la charge `CHALLENGE` reçue.
3. Le daemon vérifie en temps constant, puis répond `AUTH_OK` avec `mac = HMAC-SHA256(clé, "kory-mcp-v1|daemon|" + relay_nonce + "|" + daemon_nonce + "|" + hC + "|" + hA + "|" + proto)`, où `hA` est le base64url du SHA-256 des octets bruts de la charge `AUTH` reçue, MAC compris. Un MAC faux ou une trame malformée ferme la connexion SANS trame `ERROR`, avec une ligne dans le log du daemon : un `ERROR` serait un oracle pour qui sonde le port, et le relais ignore de toute façon un `ERROR` non authentifié (§4.5). Seul `proto_mismatch`, constaté après un MAC valide, part en `ERROR` clair.
4. Le relais vérifie ce MAC en temps constant. **Il n'envoie rien d'autre avant cette vérification** : ni environnement, ni ticket.
5. Les deux côtés dérivent les clés de session (ci-dessous). Le relais envoie `HELLO` scellé ; le daemon répond `WELCOME` ou `ERROR`, scellés.

Chaque étape a un délai de 3 s (§4.7). Un échec ferme la connexion sans verrouillage : la clé fait 256 bits.

**Encodages (fixés par la fixture `relay/protocol-fixtures/frames.json`, calculée avec `node:crypto` de bun, donc indépendante du code Rust).** La clé HMAC est formée des 32 octets obtenus en décodant les 64 caractères hexadécimaux de `mcp-daemon.key`, jamais des 64 caractères eux-mêmes. Nonces et MAC sont transmis en base64url sans padding ; les nonces entrent dans le message signé sous leur forme texte. Les MAC lient la poignée de main à sa transcription : un proxy qui modifie la charge `CHALLENGE` ou la charge `AUTH`, ou la plage de versions offerte, fait échouer la vérification de l'autre côté. Le rôle `control` est réservé au futur client de contrôle du daemon (parcours « le plus bas gagne », §6.2) : il ne signe jamais avec le rôle `relay`, et un MAC `control` ne se vérifie pas comme `relay`.

**Clés de session.** `th = SHA-256(charge CHALLENGE || charge AUTH || charge AUTH_OK)` ; `salt = daemon_nonce brut (32 octets) || relay_nonce brut (32 octets)` ; `ikm` = les 32 octets de la clé ; `k_r2d = HKDF-SHA256(ikm, salt, info = "kory-mcp-v1 r2d" || th, 32)` ; `k_d2r = HKDF-SHA256(ikm, salt, info = "kory-mcp-v1 d2r" || th, 32)`. Une clé par sens : une trame d'un sens ne s'ouvre pas dans l'autre, donc le daemon ne peut pas être forcé à rouvrir ses propres trames renvoyées. Le compteur de chaque sens part de 0. Un `ERROR` reçu avant `AUTH_OK` n'est pas authentifié : le relais passe au candidat suivant, jamais au repli bun. Un refus de version après `AUTH_OK` (`proto` hors plage) reste fatal. Écarté : chacha20-poly1305, absent de bun ; une clé commune aux deux sens ; des clés dérivées de la seule clé du fichier, qui seraient identiques d'une connexion à l'autre et permettraient le rejeu entre connexions.

**Filtre d'environnement**, appliqué par le relais : toute variable `CLAUDE_PEERS_*`, plus `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_MESSAGING_SOCKET`, `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `PATH`, `HOME`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `XDG_CONFIG_HOME`, `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` et leurs formes minuscules. Une valeur vide n'est pas transmise : sous Windows une variable vide arrive absente à l'enfant, et le daemon doit lire la même chose qu'un `server.ts` lancé directement. Le préfixe entier `CLAUDE_PEERS_*` est transmis parce que Kory ajoute des variables au fil des cartes ; le daemon ignore celles qu'il ne lit pas. Écarté : une liste fermée de noms `CLAUDE_PEERS_*`, qui ferait perdre en silence la prochaine variable de Kory. Sous Windows le relais met en majuscules le nom de toute variable retenue (`Path` devient `PATH`, `http_proxy` devient `HTTP_PROXY`), parce que le daemon lit `hello.env` comme un objet JavaScript sensible à la casse. Une variable dont le nom ou la valeur n'est pas de l'UTF-8 valide est laissée de côté et écrite dans le log du relais. Le relais ne vérifie pas les limites de 256 variables et de 64 Kio : un hello trop gros reçoit `hello_invalid`, ce qui déclenche le repli bun au démarrage (§10), avec la cause dans le log. Écarté : tronquer le hello dans le relais, qui enverrait au daemon un environnement amputé sans que personne le sache.

`pid_start` et `ppid_start` sont des chaînes opaques comparées par égalité, dont le format est fixé par OS dans la fixture (section `pid_start`) : Windows, le FILETIME de création en décimal ; Linux, le champ 22 de `/proc/<pid>/stat` compté après la dernière parenthèse ; autres unix, `ps -o lstart=`. Une chaîne vide veut dire « non mesurable ».

Le daemon valide le hello avant toute action : types, `cwd` absolu, PID entiers positifs, 256 variables au plus, 64 Kio au total. Un hello invalide reçoit `ERROR hello_invalid`. **DÉDUIT** le `host` n'est pas un champ : les sessions servies par le daemon sont toutes sur la machine du daemon (les tuiles sandbox restent sur bun, `peer-cache.ts:473-475` mentionne le cwd conteneur), donc `hostname()` reste global au daemon.

**DÉCISION, racine de code (revue critique, point 5).** Le premier relais qui lance le daemon choisit le code exécuté. **MESURÉ par la revue** (`~/.claude.json`) : la config globale pointe vers le clone `koryphaios-mcp` ; un relais d'un autre clone serait servi par l'autre code sans le savoir. Le hello porte donc `code_root`, et le daemon refuse un relais d'une autre racine par `ERROR root_mismatch`. Le relais passe alors au candidat suivant et, s'il ne trouve aucun daemon de sa racine, en lance un sur le premier port libre (§6.2) : un daemon par utilisateur et par racine, 10 au plus. Écarté : servir toute racine, ce qui exécute en silence un autre code ; refuser et passer en repli bun, ce qui laisserait mortes, après un crash, les sessions dont le daemon a été relancé par un relais de l'autre racine (pas de repli au milieu d'une session, §10). Question de confirmation Q11. `code_root` est le sha256 hexadécimal en minuscules du chemin canonique du dossier de `--fallback`, encodé en UTF-8, après retrait du préfixe `\\?\` (ou `\\?\UNC\` devenu `\\`) que `canonicalize` ajoute sous Windows. Le daemon calcule la même valeur avec `fs.realpathSync.native(import.meta.dir)`. **MESURÉ (bun, Windows 11, 2026-11-08)** : `fs.realpathSync` garde la casse saisie et les noms 8.3, `process.cwd()` garde la forme tapée, et `.native` égale `canonicalize` de Rust sur 6 entrées. Une divergence donnerait `root_mismatch` sur toutes les sessions.

### 4.5 Négociation de version

`CHALLENGE` et `AUTH` portent chacun `[proto_min, proto_max]`. Version retenue : le plus grand entier commun. Sans entier commun, le daemon répond `ERROR proto_mismatch` après un MAC valide. Cet `ERROR` arrive avant `AUTH_OK` : il n'est pas authentifié, donc le relais passe au candidat suivant (§6.2, branche `ERROR` de `authenticate` dans `relay/src/auth.rs`) et non au repli bun. **DÉCISION** : « candidat suivant » est le bon choix, car un processus qui squatterait le premier port enverrait sinon toutes les sessions en repli par un `ERROR` forgé. **Effet accepté** : un relais d'une version incompatible lance un daemon qui sort aussitôt comme doublon, puis passe en repli bun à la fin de la fenêtre de 10 s (§10). À trancher avant un proto 2. **DÉCISION** : un relais ne demande jamais l'arrêt d'un daemon incompatible. Écarté : laisser un relais récent redémarrer le daemon, ce qui couperait N sessions pour en servir une. La version 1 est la seule au départ. `daemon_version` et `relay_version` servent au diagnostic, pas à la compatibilité.

### 4.6 Ticket de reprise

**DÉCISION, format.** Le ticket est minté par le daemon et opaque pour le relais : `base64url(json) + "." + base64url(HMAC-SHA256(clé, "kory-mcp-v1|ticket|" + json))`, le préfixe séparant le domaine de ce MAC de celui de la poignée de main (§4.3). Contenu v1 : `{v: 1, family: "peers", relay_pid, relay_pid_start, writer_generation, instance_token, peer_id, group_id, notified_hwm, notice_at, outages, issued_at}`. `notified_hwm` est le plus grand id de message déjà poussé en channel. `writer_generation` est la génération du relais mesurée par le daemon précédent (§8.2), sous la forme `canonicalWriterGeneration` (256 caractères au plus) : le daemon suivant ne la remesure pas. `notice_at` et `outages` portent la date de la dernière notice de reprise et le nombre de coupures depuis : c'est ce qui permet de regrouper les notices (Q8) alors que la mémoire du daemon ne survit pas à la coupure ; un `notice_at` dans le futur est ignoré. La famille roadmap n'a pas de ticket.

**DÉCISION, séparation daemon et famille.** Le daemon fixe lui-même `v`, `family`, `relay_pid`, `relay_pid_start` et `issued_at` ; la famille ne fournit que ses propres claims (`writer_generation`, `instance_token`, `peer_id`, `group_id`, `notified_hwm`, `notice_at`, `outages`), projetées champ par champ. Écarté : laisser la famille passer un objet entier, qui pourrait écraser la liaison au relais.

**Durée de vie.** Le ticket vit dans la mémoire du relais, jamais sur disque, et meurt avec lui. Le daemon en envoie un nouveau après chaque `/register` réussi (démarrage, `switch_group`, reprise), après `set_id`, et après une poussée de channel qui fait monter `notified_hwm`, regroupé à une trame par seconde au plus. Pas d'expiration propre : l'autorité est le broker, qui accepte ou refuse le token (§8.4). `issued_at` sert aux logs.

**Vérification par le daemon suivant.** MAC valide, `relay_pid` et `relay_pid_start` égaux à ceux du hello, `family` égale. Un ticket refusé n'empêche pas la session : le daemon répond `ERROR ticket_refused` (non fatal) puis `WELCOME`, la session s'enregistre par le chemin ordinaire et le daemon envoie la notice d'identité changée (§8.3). Le ticket n'est jamais une preuve d'identité : tout relais du même compte OS peut en forger un, donc l'identité n'est gardée que si le broker répond `resumed: "token"` (§8.4). Écarté : un ticket qui ne serait qu'un identifiant de session gardé par le daemon, car il disparaît avec le daemon dont on veut survivre au crash.

### 4.7 Copie MCP, coupure, rejeu d'`initialize`

Le relais lit des lignes NDJSON sur stdin et en fait des trames `MCP`, et l'inverse sur stdout. Il analyse chaque message juste assez pour lire `id` et `method`.

- **Poignée de main.** Chaque étape (`CHALLENGE`, `AUTH_OK`, `WELCOME`) a une échéance absolue de 3 s, plafonnée à 9 s pour tout le candidat et par l'échéance d'ouverture de 10 s ; le relais ne remet pas le compteur à zéro à chaque octet reçu. Un écouteur qui envoie un octet de temps en temps ne retient donc pas l'ouverture.
- **Garde d'`initialize`.** Le relais garde en mémoire la première requête `initialize` et la notification `notifications/initialized`, octet pour octet.
- **Requêtes en vol.** Il tient l'ensemble des `id` de requêtes envoyées sans réponse, borné à 256. Une notification `notifications/cancelled` retire la requête visée (`params.requestId`) de l'ensemble : Claude l'a abandonnée, et elle ne reçoit pas d'erreur de coupure. Une ligne stdin de plus de 16 Mio renvoie une erreur pour ce seul `id`, sans couper la connexion. Le relais ré-émet vers Claude le JSON re-sérialisé sur une seule ligne ; un texte du daemon qui n'est pas du JSON est jeté avec une ligne de log.
- **Coupure.** À la fermeture de la socket, chaque requête en vol reçoit une erreur JSON-RPC `-32000` : « claude-peers daemon connection lost; this call may or may not have been executed ». Le texte dit « may have been executed » parce que `send_message` n'est pas idempotent. Toute nouvelle requête reçoit, tant que le daemon est absent : « claude-peers daemon unreachable: this call was NOT executed, retry it once the daemon is back ». La requête n'est ni transmise ni mise en file : le modèle doit la rejouer. Les notifications de Claude vers le serveur sont jetées.
- **Reconnexion.** Délai de 100 ms doublé jusqu'à 5 s, avec une gigue de 0 à 25 % du délai courant, sans limite de tentatives tant que stdin est ouvert. Chaque tentative parcourt les candidats ; l'absence de daemon de sa racine déclenche la course de démarrage (§6.2). Quand un daemon répond mais refuse la session (`hello_invalid`, version), chaque appel d'outil reçoit une erreur qui nomme la cause (« a daemon is running but refuses this session: <cause> »), le relais journalise une ligne par passage, le délai reste borné à 5 s, et il ne lance **jamais** un second daemon tant qu'un daemon existant refuse.
- **Rejeu.** Après `WELCOME`, le relais envoie la requête `initialize` gardée avec un `id` réécrit en `"kory-relay-replay-<n>"`, attend la réponse portant cet `id` et l'avale, puis envoie la `notifications/initialized` gardée. Les requêtes de Claude arrivées pendant le rejeu attendent en file, 64 au plus et 5 s au plus ; au-delà elles reçoivent l'erreur de coupure. Écarté : rejouer avec l'`id` d'origine, qui pourrait croiser un `id` que Claude réutilise.
- **Liste d'outils.** `WELCOME.tools_hash` est un condensat de la liste servie. Si elle diffère de celle de la connexion précédente, le relais émet `notifications/tools/list_changed`. **SUPPOSÉ** : Claude Code relit la liste à cette notification pour un serveur stdio ; non mesuré en L1, reporté à L2 (session interactive et vrai daemon) ; la liste ne change qu'avec le code du daemon.
- **PING.** Le relais envoie `PING` toutes les 15 s ; sans `PONG` en 10 s, il ferme la connexion et suit le chemin de coupure.
- **Daemon bloqué (revue critique, point 1).** Un daemon dont la boucle d'événements est bloquée accepte encore les connexions au niveau du noyau, ne répond plus, et garde le port : sans action, aucune relance n'est possible et les sessions restent en erreur, car il n'y a pas de repli en cours de session. **DÉCISION** : après 30 s pendant lesquelles chaque tentative a obtenu une connexion sans `CHALLENGE` dans les 3 s, le relais lit `mcp-daemon-<port>.json` (§6.2), vérifie que le PID est vivant, que son heure de création égale `pid_start` et que son image est `kory-mcp-daemon` (ou `bun` en repli de nom, §6.1), puis l'arrête et relance la course de démarrage. Plusieurs relais qui arrêtent le même PID sont sans effet de bord. Le PID n'est jamais pris dans un fichier dont `pid_start` ne correspond pas : un PID réutilisé n'est pas tué. Écarté : ne jamais tuer le daemon, ce qui laisse N sessions mortes jusqu'à une action de l'opérateur. Le relais n'arrête un daemon que si le `code_root` du fichier d'état égale le sien : un daemon bloqué d'une autre racine n'est jamais arrêté par ce relais. Chaque refus d'arrêt (fichier illisible, PID mort, PID réutilisé, image refusée, autre racine) laisse une ligne dans son log. Un PID de 0 ou supérieur à `i32::MAX` n'est jamais arrêté : sous POSIX il désignerait un groupe de processus.
- **Fin.** EOF de stdin : `BYE {reason: "stdin_eof"}`, fermeture, sortie 0, et la boucle de reconnexion s'arrête. Le motif `signal` n'est pas émis par le relais : il demanderait un gestionnaire de signal par OS, et le daemon traite déjà une socket fermée sans `BYE` comme une fin de session (§6.3). Le daemon accepte donc `signal` en réception, sans qu'aucun relais de ce lot l'envoie.

La notice de reconnexion est émise par le daemon, pas par le relais : c'est le daemon qui sait si la reprise a gardé l'identité (§8.3).

## 5. Authentification du canal et modèle de menace

**Modèle de menace, énoncé explicite.**

- **Protégé** : un autre compte OS de la même machine. Il peut capturer le loopback (Npcap, avec ses réglages par défaut, laisse un compte non administrateur le faire), mais il ne lit rien : tout ce qui suit `AUTH_OK` est scellé par AES-256-GCM (§4.2), et les MAC et les clés de session sont liés à la transcription de la poignée de main (§4.3). Il ne peut ni se connecter au daemon, ni se faire passer pour lui auprès d'un relais, ni modifier, injecter, rejouer ou réfléchir une trame, ni se placer en proxy sans connaître la clé.
- **Non protégé, par construction** : tout processus du même utilisateur. Il lit déjà les fichiers d'identité de `~/.claude/peers` (tokens d'instance), le fichier de réglages (`broker_token`), les fichiers `.claude-peers.json` (secrets de groupe) et l'environnement des processus `claude.exe`. Il peut lancer `bun server.ts` avec n'importe quel environnement. Le daemon ne lui donne aucune capacité nouvelle. Il garde en mémoire les tokens de toutes les sessions, mais aucune trame ne permet à une connexion de lire l'état d'une autre.
- **Hors périmètre** : l'administrateur de la machine.

**DÉCISION, clé partagée.** 32 octets aléatoires, en hexadécimal, dans `<home>/.claude/peers/mcp-daemon.key`, le dossier qui porte déjà les fichiers d'identité. **DÉCISION du lead, 2026-11-08, validée par le security-auditor** : seul le relais crée la clé. Le daemon ne la crée jamais et ne la répare jamais : il l'audite au démarrage et refuse de démarrer si elle manque ou si son ACL est ouverte, avec la cause dans son log ; le relais retombe alors en repli bun. **MESURÉ** (`relay/src/lib.rs`) : le relais charge ou crée toujours la clé avant de lancer le daemon, car `load_or_create_key` précède `find_session`. Pour la créer, le relais écrit un fichier temporaire au nom aléatoire dans le même dossier, puis crée un lien dur vers `mcp-daemon.key` sur les trois systèmes. Un lien dur échoue si la cible existe et ne laisse jamais voir un fichier partiel ; le perdant relit le fichier du gagnant, et le temporaire est supprimé dans tous les cas. Écarté : `MoveFileEx` sans remplacement sous Windows, qui donne la même garantie avec une dépendance de plus. Sous Linux et macOS, le relais et le daemon refusent une clé qui n'appartient pas à l'uid courant ou qui accorde un droit au groupe ou aux autres (`mode & 0o077 == 0` exigé). Son dossier peut être lisible (`~/.claude/peers` est créé en 0755 par d'autres écrivains) mais ne doit pas être inscriptible par le groupe ou les autres (`mode & 0o022 == 0` exigé), car un dossier inscriptible permet à un autre compte de remplacer le fichier de clé. Le relais crée le dossier en 0700 quand c'est lui qui le crée. Écarté : exiger 0700 du dossier, qui ferait passer toutes les sessions en repli. Un refus passe en repli. **DÉCISION de l'opérateur, 2026-11-08** : sous Windows, la clé porte une DACL protégée (héritage coupé ; seuls l'utilisateur courant, SYSTEM `S-1-5-18` et Administrateurs `S-1-5-32-544`, en contrôle total). Le relais la crée DÉJÀ protégée : `CreateFileW` avec un descripteur de sécurité protégé, avant d'écrire le moindre octet du secret. **MESURÉ par une sonde** : Windows ne contrôle l'accès qu'à l'ouverture d'un handle, donc un fichier créé avec l'ACL héritée puis protégé reste lisible par un compte qui l'a ouvert entre-temps. Avant de lancer le daemon, le relais répare une clé dont la DACL hérite, donne un droit à un autre SID ou n'a pas d'entrée pour l'utilisateur courant, et écrit une ligne de log par réparation ; si la réparation échoue, la clé est refusée et la session passe en repli. Le daemon audite cette DACL mais ne la répare pas (voir ci-dessus). Cela remplace l'hypothèse « profil non partagé ». **Cause mesurée** : `mcp-daemon.key` héritait d'une ACE explicite `(OI)(CI)(RX)` pour `CodexSandboxUsers` posée sur `%USERPROFILE%\.claude`. **Risque accepté** : le propriétaire du fichier n'est pas vérifié sous Windows (l'équivalent de la règle d'uid de Unix). Pas de rotation automatique ; supprimer le fichier puis redémarrer le daemon fait tourner la clé.

**Pourquoi mutuelle.** Sans la preuve du daemon, un autre compte qui écoute le premier sur le port reçoit les hellos, donc les secrets de groupe forcés par Kory. C'est le risque principal du TCP local. Le loopback n'est pas une identité. Sans scellement, un proxy qui laisserait passer la poignée de main pourrait lire puis injecter des trames, car rien ne serait authentifié après `AUTH_OK`.

**Conteneurs sandbox (revue critique, point 6).** **DÉDUIT par la revue, non relu ici** : un conteneur joint le loopback de l'hôte (`desktop/src/main/sandbox-command.ts:289`) et peut ouvrir des connexions au daemon ; la clé n'est pas montée dans le conteneur (`sandbox-command.ts:305-357`), donc l'authentification tient. **DÉCISION** : le daemon borne les connexions non authentifiées à 32 en même temps et à 9 s de vie (trois étapes de 3 s) ; au-delà, une nouvelle connexion est fermée tout de suite et comptée dans `status`. Une connexion authentifiée compte dans la borne de sessions (§7.5). Écarté : filtrer par adresse source, qui ne distingue pas un conteneur passé par le pont de Docker Desktop d'un processus hôte (**SUPPOSÉ**).

## 6. Cycle de vie du daemon

### 6.1 Démarrage par le relais

**DÉCISION.** Le relais qui gagne le verrou de lancement (§6.2) exécute `<dossier du fallback>/mcp-daemon.ts` avec l'image `kory-mcp-daemon` (ci-dessous), lancé :

- détaché, sans fenêtre : `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP | CREATE_BREAKAWAY_FROM_JOB` sous Windows, `setsid` sous POSIX ;
- avec cwd = `<home>/.claude/peers`, jamais le cwd de la session : sous Windows, un cwd ouvert empêche de supprimer le dossier, et Kory retire des worktrees ;
- avec stdout et stderr ouverts en ajout sur `<coreLogDir>/mcp-daemon.out.log`, pour capter une panique au chargement ;
- avec un **environnement filtré** : bases OS (`SystemRoot`, `windir`, `ComSpec`, `PATH`, `PATHEXT`, `TEMP`, `TMP`, `HOME`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `XDG_*`, `LANG`, `TZ`), proxys, et seulement ces réglages globaux au daemon : `CLAUDE_PEERS_LOG_DIR`, `CLAUDE_PEERS_POLL_FALLBACK_SEC`, `CLAUDE_PEERS_CONTEXT_RESUME_KEY_TTL_MS`, `CLAUDE_PEERS_MCP_DAEMON_*`. Aucune variable de session.

Écarté : hériter l'environnement du premier relais, qui donnerait au daemon le groupe forcé de la première tuile Kory venue.

**La clé existe avant le lancement (DÉCISION du lead, 2026-11-08, validée par le security-auditor).** Le relais charge ou crée la clé, et la répare au besoin (§5), avant de lancer le daemon : `load_or_create_key` précède `find_session` dans `relay/src/lib.rs`, et la reconnexion réutilise la clé déjà chargée. Le daemon ne crée ni ne répare la clé : il l'audite et refuse de démarrer si elle manque ou si son ACL est ouverte, avec la cause dans son log, et le relais retombe alors en repli bun (§10). Un daemon lancé à la main avant tout relais s'arrête donc faute de clé.

**Ceinture et bretelles.** Au démarrage, le daemon retire de son propre `process.env`, et le journalise, toute variable de session (`CLAUDE_PEERS_FORCE_GROUP*`, `CLAUDE_PEERS_GROUP`, `CLAUDE_PEERS_DESK_*`, `CLAUDE_PEERS_ROLE`, `CLAUDE_PEERS_SUPERVISOR`, `CLAUDE_PEERS_TOOLS`, `CLAUDE_PEERS_APPROVAL_FILE`, `CLAUDE_PEERS_DEPOSIT_CAPABILITY`, `CLAUDE_PEERS_BROKER_*`, `CLAUDE_CODE_*`). Un daemon lancé à la main depuis le shell d'une tuile ne peut donc pas prêter son groupe. La garantie principale reste le §7.3 : les helpers n'ont plus de valeur par défaut.

**MESURÉ (Claude Code 2.1.318, Windows 11, 2026-11-06)** : un enfant lancé par un serveur MCP stdio survit à la fin de la session, que ce soit un `claude -p` qui se termine ou une session interactive dont l'opérateur ferme la fenêtre de terminal. Les trois variantes survivent : sans option, avec `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`, et avec `CREATE_BREAKAWAY_FROM_JOB` en plus, qui n'échoue pas. Claude Code ne tue donc pas les enfants de ses serveurs MCP à la fermeture. Le relais garde les options détachées ci-dessus, pour ne dépendre ni de la console ni d'un futur job. Le repli WMI n'est pas nécessaire hors Kory.

**MESURÉ, cas d'une tuile Kory (2026-11-06)** : sous Windows, chaque tuile entre dans un job Windows (`JOB_PREAMBLE_PS`, `desktop/src/main/shell-command.ts`) avec `KILL_ON_JOB_CLOSE` (0x2000) et sans `BREAKAWAY_OK` (0x800). Avec le préambule réel, un enfant sans option ou détaché MEURT quand le PowerShell de la tuile se termine, et `CREATE_BREAKAWAY_FROM_JOB` échoue avec « Accès refusé ». Un daemon lancé depuis une tuile mourrait donc avec elle et couperait toutes les sessions, Kory ou non. Avec les limites `0x2800`, l'enfant `CREATE_BREAKAWAY_FROM_JOB` survit, et les enfants ordinaires meurent toujours : l'arrêt de l'arbre de la tuile reste intact. Décision : L2 ajoute `BREAKAWAY_OK` au job des tuiles, et le relais lance le daemon avec `CREATE_BREAKAWAY_FROM_JOB`. Si cette option échoue (Kory d'une version antérieure), le relais la retire, lance le daemon quand même, et le journalise : ce daemon mourra avec la tuile, et un autre relais le relancera. Contrepartie de sécurité à accepter : tout processus d'une tuile peut désormais sortir du job en le demandant, donc échapper à l'arrêt de l'arbre. C'est du code du même utilisateur, qui pouvait déjà lancer un processus hors de Kory. À remesurer si une version de Claude Code change ce comportement : le test de L6 ferme la session qui a lancé le daemon et vérifie qu'il sert encore la seconde.

**Nom de processus distinct (DÉCIDÉ par l'opérateur le 2026-11-06).** Le daemon apparaît sous le nom `kory-mcp-daemon` dans le gestionnaire des tâches, `ps` et `top`, pour que l'utilisateur le distingue des autres processus bun. Le relais ne lance donc pas `bun` directement, mais une image nommée `kory-mcp-daemon` :

- **Windows** : une copie de `bun.exe` sous `<home>/.claude/peers/bin/kory-mcp-daemon.exe`. MESURÉ (bun 1.3.13) : une copie renommée de `bun.exe` exécute un script `.ts` normalement et apparaît sous son nouveau nom dans `tasklist` ; `process.execPath` vaut le chemin de la copie. Le relais refait la copie quand elle manque ou quand sa taille ou sa date diffère du `bun.exe` résolu, pour suivre une mise à jour de bun. Écarté : un lien dur, qui garde l'ancien binaire quand `bun upgrade` remplace le fichier.
- **Linux et macOS** : un lien symbolique `kory-mcp-daemon` vers `bun` dans le même dossier. SUPPOSÉ, à mesurer en L5 : le nom du processus (`comm`) est celui du chemin exécuté, donc celui du lien.
- **Repli** : si la copie ou le lien échoue (disque plein, droits), le relais lance `bun` sous son nom, et le journalise.
- **Effet de bord voulu** : un `taskkill /IM bun.exe` (règle « Shared checkout » du dépôt) n'arrête plus le daemon.

### 6.2 Instance unique et course au démarrage

**Recherche par le relais.** Il se connecte aux 10 candidats en même temps (un fil par candidat), puis traite les résultats dans l'ordre des ports. **MESURÉ (Windows 11, rustc 1.94, `TcpStream::connect` et `connect_timeout`, 2026-11-08)** : une connexion à un port loopback fermé rend `ConnectionRefused` après 2 045 ms, et `connect_timeout` de 300, 1 000 ou 1 500 ms rend `TimedOut` ; Linux et macOS refusent aussitôt. Un balayage séquentiel de 10 ports libres coûterait donc environ 20 s, au-delà de la fenêtre d'ouverture de 10 s (§10). **DÉCISION** : un port dont la connexion est refusée, ou n'a pas abouti à `connect_timeout` (1 s par défaut), est noté libre ; un port qui écoute termine la connexion dans le noyau aussitôt. Connexion acceptée : poignée de main ; un échec d'authentification, `root_mismatch`, une réponse qui n'est pas du protocole ou un `ERROR` non authentifié fait passer au suivant. Le premier `WELCOME` dans l'ordre des ports termine la recherche. Le relais ne parle donc qu'au daemon de sa racine au port le plus bas. Cas accepté : un daemon vivant dont la file d'attente de connexions est pleine peut être pris pour libre ; le relais lance alors un second daemon, qui sort comme doublon grâce à la règle du port le plus bas. Écarté : un balayage séquentiel, trop lent sous Windows ; ouvrir une session sur chaque daemon trouvé puis fermer les surplus, qui enverrait le hello et ses secrets à des daemons inutiles. Le balayage « le plus bas gagne » du daemon (paragraphe suivant) n'a pas ce coût côté bun : **MESURÉ (bun, Windows 11, 2026-11-08)**, une connexion à un port fermé rend `ECONNREFUSED` en 3 à 11 ms, et 10 connexions en parallèle prennent 8 ms. Les environ 2 s sont propres au `connect` bloquant de la bibliothèque standard de Rust. **Connexion de poignée de main ouverte au tour du candidat.** Les connexions parallèles ne servent qu'à classer les ports (libre ou à l'écoute) et sont refermées aussitôt ; la poignée de main se fait sur une connexion neuve, ouverte quand vient le tour du candidat. Un daemon coupe une connexion dont l'étape de poignée de main dépasse `STAGE_MS` (3 000 ms, `Connection.arm`). **MESURÉ (journaux des relais, 2026-11-10)** : 17 relais notent `port 47176: ... (os error 10054), skipped`. Avec une connexion gardée ouverte depuis la recherche, un candidat plus bas qui écoute sans répondre (un port fantôme, voir « Broker avant l'écoute ») coûtait au relais `step_timeout` ; pendant ce temps le vrai daemon, plus haut, coupait la connexion en attente, et le relais se repliait sur bun. Écarté : garder la connexion de la recherche pour le premier candidat qui écoute, qui ne tient que si tous les ports plus bas sont réglés avant. **Port libre au sondage, réessayé à son tour.** Si le sondage date de plus de `connect_timeout` quand vient le tour d'un port classé libre, le relais s'y reconnecte une fois, avec un délai borné à 50 ms ; sans cela, un daemon qui se met à écouter pendant que le relais attend sur un candidat muet plus bas resterait manqué pour toute la passe (démarrage groupé). **MESURÉ (Rust, Windows 11, 2026-11-10, 30 essais)** : un connect refusé avec l'option sans retransmission de SYN coûte 0,2 ms en médiane (maximum 25 ms, premier appel) ; sans l'option, `connect_timeout` de 50 ms rend `TimedOut` après 61 ms et un `connect` bloquant 2 040 ms ; un connect vers un port qui écoute coûte 0,09 ms. Une passe de 10 ports libres atteint tous ses tours avant `connect_timeout`, donc ne réessaie rien et garde le coût de la recherche parallèle ; après une attente sur un muet, le pire cas (option non appliquée) est de 61 ms par port libre. **Trace.** Un candidat muet laisse la ligne `port <n>: no CHALLENGE within <ms>, skipped (silent listener)`, et la cause du repli à la fin de la fenêtre d'ouverture cite les ports muets vus (`silent listeners seen on ports ...`).

**Verrou de lancement (revue critique, point 2).** Après un crash, N relais trouvent les candidats vides en même temps. Lancer N fois bun coûte N démarrages et N mesures de génération (§8.2). **DÉCISION** : seul le relais qui crée en exclusif `<home>/.claude/peers/mcp-daemon-<code_root 8>.launch` (son PID et l'heure) lance le daemon. Les autres reprennent la recherche avec un délai aléatoire de 200 à 800 ms. Le fichier est supprimé par le daemon après `listen` et aussi quand il sort comme doublon, et considéré périmé après 15 s ou si son PID est mort ; un relais le remplace alors. Écarté : laisser chaque relais lancer et le port départager, ce qui produit exactement la tempête décrite. Le relais qui vient de prendre le verrou refait un balayage complet avant de lancer ; s'il trouve le daemon, il supprime lui-même le verrou qu'il vient de créer. **Reprise d'un verrou périmé** : seul le relais qui crée en exclusif `mcp-daemon-<code_root 8>.takeover` peut le retirer ; sous ce marqueur il juge la péremption une seconde fois, puis renomme le verrou vers un nom unique et le supprime. **MESURÉ** : sans ce marqueur, un renommage ou une suppression par chemin retire parfois le verrou frais qu'un autre relais vient de créer (2 gagnants sur 8 fils). Un marqueur périmé (PID mort ou 15 s) est déplacé vers un nom unique, jugé de nouveau et remis en place s'il est frais. Une comparaison suivie d'une suppression n'est pas atomique sur un fichier : la fenêtre qui reste coûte deux relais qui lancent un daemon, et la règle du port le plus bas en laisse un. Sous Windows seulement, une erreur « accès refusé » à la création du verrou ou du marqueur compte pour « occupé », pas pour une panne : **MESURÉ**, la création pendant qu'un autre relais supprime ou renomme le même chemin rend cette erreur et non « existe déjà ». Sous POSIX, un refus de droits (`EACCES`) reste une erreur : le traiter comme « occupé » masquerait un vrai défaut de droits et ferait écrire des lignes sans reculer. Écarté : un verrou de fichier du système, que le daemon bun ne peut pas relâcher à son `listen`.

**Le plus bas gagne, côté daemon.** Au démarrage, le daemon parcourt les candidats. Pour chaque port occupé plus bas que celui qu'il vise, il se connecte comme client, s'authentifie et demande `CONTROL status`. Si ce daemon a la même racine, le nouveau sort avec le code 0 : il est en double. Sinon il prend le premier port libre. Un `EADDRINUSE` au `listen` relance le parcours. Après un `listen` réussi sur un port qui n'est pas le premier, il refait une fois le parcours des ports plus bas et sort s'il y trouve un daemon de sa racine, pour couvrir la course entre son parcours et son `listen`. Écarté : port unique sans parcours, incompatible avec la décision des 10 candidats.

**Broker avant l'écoute.** Avant son premier `listen`, le daemon assure le broker local de sa propre configuration (`brokerBeforeListen` de `runDaemon`, attente bornée à 3 s). **MESURÉ (bun, Windows 11, 2026-11-10)** : un processus lancé avec `node:child_process` (`detached`, `stdio: "ignore"`) pendant que le daemon écoute hérite du socket d'écoute ; le port reste `LISTENING` au nom du daemon mort tant que ce processus vit, et un relais qui s'y connecte attend en vain. Le broker lancé par le daemon survit au daemon, d'où le port fantôme. Lancé avant le `listen`, il n'hérite de rien. Seul le lancement doit précéder le `listen` : au-delà de 3 s, le daemon écoute sans attendre le `/health`. Le broker est celui de la configuration du daemon (fichier de configuration et variables que le nettoyage de l'environnement laisse), et seulement en mode local : en mode réplica ou distant, le daemon note `broker not pre-ensured: <mode>` et écoute, car l'URL amont d'une session posée par variable d'environnement lui est invisible. Limite : un broker relancé plus tard par une session, daemon à l'écoute, reste lancé avec le socket hérité. **MESURÉ** : un lancement par `Start-Process` ou par `Win32_Process.Create` de WMI, depuis un `powershell.exe` non détaché, ne fuit pas le socket ; `powershell.exe` lancé avec `detached: true` ne lance rien.

**Fichier d'état.** Après `listen`, le daemon écrit `<home>/.claude/peers/mcp-daemon-<port>.json` (`pid`, `pid_start`, `port`, `code_root`, `code_fingerprint`, `version`, `instance`, `started_at`) par écriture atomique, et le supprime à l'arrêt. Il sert au diagnostic et à l'arrêt d'un daemon bloqué (§4.7) ; aucun relais ne s'y fie pour trouver le daemon.

**MESURÉ (bun, Windows 11, 2026-11-08)** : sous Windows, un second `listen` du même utilisateur sur le même port échoue avec `EADDRINUSE`, comme il le faut : sinon, deux daemons serviraient chacun une partie des sessions. Quand un autre processus tient `0.0.0.0:<port>`, le `listen` rend `EACCES`, que le daemon traite comme « port pris ». Le test le vérifie (§12, L2).

### 6.3 Arrêt

- **Inactivité (Q2, DÉCIDÉ).** Sortie après `CLAUDE_PEERS_MCP_DAEMON_IDLE_SEC` secondes sans aucune connexion de session (600 par défaut, 0 pour jamais). Le gain mémoire vise les heures sans session, et la sortie fait prendre le nouveau code au prochain démarrage. Écarté : ne jamais s'arrêter, ce qui garderait environ 200 Mo et l'ancien code indéfiniment.
- **Ordre de l'arrêt sur inactivité (revue critique, point 7).** **DÉCISION** : fermer d'abord l'écoute, attendre la fin des poignées de main en cours (9 s au plus), puis vérifier une dernière fois le nombre de sessions. Zéro : sortie. Sinon le daemon rouvre l'écoute sur le même port ; si un autre daemon l'a pris entre-temps, il continue de servir ses sessions sans écouter et sort quand la dernière se ferme. Écarté : vérifier puis fermer, ce qui laisse entrer un relais entre les deux et le coupe aussitôt.
- **Arrêt demandé** (`CONTROL stop`, SIGTERM, SIGINT) : le daemon ferme la socket de chaque relais, puis la session avec `close("daemon_stop")`, **sans** `/disconnect` et sans toucher au fichier d'identité de tuile ni au snapshot (§7.1). Les sessions sont vivantes, leurs relais se reconnectent et reprennent. Un `/disconnect` libérerait en RAM les dépôts de contexte de chaque session (`ARCHITECTURE.md`, « Context deposits »).
- **Fin d'une session** (`BYE`, ou socket fermée par le relais) : `close("bye")` ou `close("socket")`, bornés à 5 s par le daemon, avec suppression des fichiers d'identité et `/disconnect` (§7.1).

### 6.4 Mise à jour du code avec des sessions ouvertes

**DÉCISION : une mise à jour est un crash contrôlé.** Le daemon calcule au démarrage l'empreinte de son code (sha256 du point d'entrée et de ses modules, ou d'un bundle en L5) et la publie dans `status`. `bun cli.ts mcp-daemon status` compare cette empreinte au code sur disque et affiche « daemon code is stale » le cas échéant. `bun cli.ts mcp-daemon restart` envoie `CONTROL stop` au daemon de la racine du clone qui l'exécute : les relais se reconnectent, relancent le nouveau daemon et reprennent par ticket. C'est le chemin que le crash doit déjà suivre, donc le seul à tester. Sans réponse à `CONTROL stop` en 5 s (daemon bloqué, revue critique, point 1), la commande arrête le PID du fichier d'état avec les mêmes vérifications que le relais (§4.7). Procédure dans `README.md` (Q7, DÉCIDÉ : CLI seule). La CLI existe (`shared/mcp-daemon-status.ts`, branchée dans `cli.ts`) : elle lit la clé sans la créer ni la réparer, et sans clé elle le dit et ne fait rien. Sous POSIX elle refuse une clé ouverte au groupe ou aux autres ; sous Windows elle ne contrôle pas l'ACL, ce qui reste le travail du relais et du daemon. Un relais plus récent que le daemon et sans version commune passe en repli pour sa session (§4.5). Écarté : un daemon qui surveille ses fichiers et redémarre seul pendant une écriture de l'opérateur.

### 6.5 Logs et visibilité

- Daemon : le puits existant `<coreLogDir>/server.log`, avec un logger enfant par session dont chaque ligne porte `s=<session_id 8>` et, une fois enregistré, `peer=<peer_id>`. Les lignes de cycle de vie portent `daemon`. Les serveurs bun de repli continuent d'écrire le même fichier, comme aujourd'hui N processus. stdout et stderr : `mcp-daemon.out.log`.
- Relais : stderr seulement, une ligne par événement, préfixée `claude-peers-relay[<famille> <pid>]`, captée par Claude Code dans ses logs MCP. Aucun échec n'est silencieux : connexion, MAC, trame scellée refusée, hello, lancement du daemon, retrait de `CREATE_BREAKAWAY_FROM_JOB`, arrêt ou refus d'arrêt d'un daemon bloqué, variable d'environnement écartée, perte de connexion, reconnexion avec le nombre de notifications perdues, repli bun avec sa cause.
- Opérateur : un outil appelé pendant une coupure répond par l'erreur explicite du §4.7. `bun cli.ts mcp-daemon status` parcourt les 10 candidats et dit, pour chaque daemon : vivant, sans réponse ou périmé, avec sa racine ; il liste aussi les sessions en repli bun (Q5, §10). La notice de reconnexion arrive en channel dans les sessions peers.

### 6.6 Kory ne possède pas le daemon

Kory ne le lance pas, ne l'arrête pas et ne l'attend pas. Quitter Kory n'arrête pas le daemon. Une tuile Kory est une session comme une autre ; ce qui la distingue (groupe forcé, jeton de tuile, credential de run, capability de dépôt) arrive dans son hello. Le Deck peut afficher l'état du daemon par `CONTROL status`. C'est facultatif et hors de ce chantier.

## 7. Modèle d'état par session

### 7.1 Fabriques

**DÉCISION, deux couches.** Le daemon ne connaît que des **familles** ; la famille peers construit une **session** à partir du hello. La session ne sait rien du transport qui la sert : le même `createPeersSession` sert l'entrée stdio (`server.ts`) et le daemon (`shared/peers-family.ts`).

```ts
// shared/mcp-daemon-server.ts : la couture du daemon
type FamilyFactory = (hello: Hello, ctx: FamilyContext) => Server | FamilyHandle | Promise<Server | FamilyHandle>;
interface FamilyHandle { server: Server; close(reason: "bye" | "socket" | "daemon_stop"): Promise<void> }
interface FamilyContext {
  sessionId: string; log: Logger; home: string;
  resume: { kind: "none" } | { kind: "accepted"; claims } | { kind: "refused"; cause };
  issueTicket(claims: FamilyTicketClaims): void;   // peers seulement, regroupé à une trame TICKET par seconde
  brokers: BrokerEnsurer; settings: DaemonSessionSettings;
}

// shared/peers-session.ts : la session, sans process.*
createPeersSession(input: PeersSessionInput, deps: PeersSessionDeps): PeersSession
interface PeersSession extends FamilyHandle {
  readonly ready: Promise<void>;   // enregistrée et fichiers d'identité écrits ; un broker absent est réessayé, pas rejeté
  openChannel(): void;             // WS, heartbeat, poll et notice de reprise ; à appeler une fois le transport connecté ; rejouable
  identity(): LinkedIdentity | null;  // null avant l'enregistrement et pendant un changement d'identité (§9)
}
```

Une famille qui rend un `Server` nu (roadmap) est enveloppée par le daemon dans un handle dont `close` ne fait rien. `Session.close` du daemon appelle le `close(reason)` de la famille avant `server.close()`, borné à 5 s ; `stop()` du daemon attend les fermetures déjà commencées. Le `Server` MCP est connecté à un transport sur des trames `MCP` dans le daemon, sur `process.stdin` et `process.stdout` dans l'entrée bun. Chaque session construit son propre `Server` et ses handlers en fermeture sur son contexte. Aucune fabrique n'appelle `process.*` ; la fabrique de famille lit tout dans le hello (PID et ppid du relais enregistrés comme `pid` et `client_pid`, cwd, env, tty) et dans `ctx` (home, réglages du daemon par-dessus les défauts, `resume`, `issueTicket`, `brokers`). Écarté : une fabrique qui recevrait le transport, ce qui lierait la session au daemon et empêcherait l'entrée stdio de la réutiliser.

**Ouverture d'une session peers.** Validation du hello, `WELCOME`, service MCP immédiat (`initialize` et `tools/list` ne dépendent que du hello), puis enregistrement en tâche de fond. Un `tools/call` attend `ready`, 30 s au plus. Un broker absent n'est pas un échec du serveur MCP : la session réessaie l'enregistrement avec un délai doublé quand le broker ne répond pas ou quand le lanceur de broker dit « réessayable » (§11), et chaque appel d'outil répond la dernière erreur en attendant. **Même règle en stdio** : `server.ts` connecte le transport MCP et installe ses gestionnaires de sortie **avant** la fin de l'enregistrement, répond `initialize` avant lui, et réessaie un `/register` resté sans réponse HTTP au lieu de sortir en erreur. Un EOF de stdin pendant un réessai sort donc avec le code 0 et aucun pair fantôme ne s'enregistre plus tard. Un échec du lanceur de broker reste fatal en stdio. Écarté : refuser le hello, ou sortir du processus stdio, si le broker ne répond pas, ce qui transformerait un broker lent à démarrer en serveur MCP en échec. Conséquence pour les tests : un harnais qui lance le compagnon roadmap après l'entrée stdio attend d'abord un `whoami`, car la réponse à `initialize` ne prouve pas que le snapshot d'identité existe.

**Fermeture.** Annule toutes les minuteries de la session, le résumé en cours, les attentes `wait_for_message` (signal de session composé avec `extra.signal`), arrête la reconnexion WS et ferme la WS, interrompt les appels d'identité en vol avec le signal de session, puis : pour `bye` et `socket`, supprime le fichier d'identité de tuile (gardé, §7.3) et le snapshot global de la session, puis `/disconnect`, le tout sous une échéance partagée (3 s pour `/disconnect` en stdio). **DÉCISION** : `close("daemon_stop")` ne supprime ni le fichier d'identité de tuile ni le snapshot, et ne fait pas de `/disconnect` : un arrêt du daemon est un crash contrôlé (§6.3), la session est vivante et son relais va reprendre par ticket ; les lecteurs du fichier de tuile gardent un token valide pendant la coupure (§8.3). Écarté : supprimer les fichiers à tout `close`, ce qui laisserait la roadmap et le Deck sans identité pendant chaque mise à jour du daemon.

**Sérialisation.** Les opérations qui changent l'identité (`register`, `switch_group`, `set_id`) passent par une chaîne de promesses propre à la session. Les minuteries lisent le contexte au moment de l'appel, comme aujourd'hui.

### 7.4 `process.exit`, signaux, rejets

- **Fabriques** : aucun `process.exit`, `process.on` ou accès à `process.stdin` ou `process.stdout`.
- **Entrées stdio** (`server.ts`, `server-roadmap.ts`) : gardent la politique actuelle, une session par processus. `uncaughtException` et `unhandledRejection` journalisent puis `exit(1)` ; SIGINT, SIGTERM et EOF de stdin ferment la session puis `exit(0)`, y compris pendant un réessai d'enregistrement, puisque ces gestionnaires sont installés avant lui (§7.1). `server-deck.ts` journalise dans `server-deck.log`.
- **Daemon** : `unhandledRejection` journalise et continue. `uncaughtException` journalise ; plus de 5 en 60 s provoque un arrêt contrôlé (§6.3), suivi de reconnexion et de reprise. SIGINT et SIGTERM : arrêt contrôlé. Le point d'entrée du daemon n'importe aucun module qui installe un gestionnaire de processus. Chaque handler MCP et chaque minuterie de session s'exécute dans un `try/catch` qui journalise avec l'étiquette de la session. Écarté : un `exit(1)` du daemon à chaque rejet, qui transformerait le bug d'une session en coupure de N.

## 8. Vivacité et identité

### 8.1 PID enregistrés

**DÉCISION.** `pid` et `client_pid` de `/register` = PID du relais ; `pid_generation` = génération du relais (§8.2). Le PID du daemon n'est jamais envoyé au broker. Sinon `cleanStalePeers` verrait toutes les sessions vivantes tant que le daemon tourne. Le relais vit exactement aussi longtemps que la session MCP : il sort sur EOF de stdin.

**`claude_cli_pid` (revue critique, point 8).** **MESURÉ**, `git grep -n "claude_cli_pid" -- ':!tests' ':!docs' ':!*.md'` : seulement la migration, des listes de colonnes d'écriture et des commentaires (`broker.ts:651,2238,2272,2824,...`, `server.ts:2069`). Aucun lecteur. Le commentaire `broker.ts:648` qui parle du hook SessionEnd est périmé. **DÉCISION** : le daemon envoie `claude_cli_pid = hello.ppid` dans les deux sites d'enregistrement, par parité de corps, mais aucune règle ne s'appuie dessus : ni la reprise (§8.4), ni la vivacité. Écarté : en faire une preuve de reprise, alors qu'aucun code ne le lit ni ne le vérifie.

**Vivacité pendant une coupure (Q9, DÉCIDÉ).** En modes `local` et `replica`, le broker garde un pair actif tant que le PID de relais enregistré est vivant sur son hôte, même sans heartbeat. Une coupure du daemon de plus de 120 s ne rend donc plus le pair dormant, et ses dépôts de contexte survivent (le propriétaire d'un dépôt doit être actif, `ARCHITECTURE.md`, « Context deposits »). En mode `remote`, le broker ne sonde pas un PID étranger : la limite de 120 s du balayage demeure, et c'est documenté. Contrat broker : §8.4, règle V.

### 8.2 Génération d'auteur du snapshot

Le daemon écrit le snapshot global (`global-session-identity-<sha256(socket)>.json`) au nom de la session. **DÉCISION** : la génération enregistrée est celle du relais peers, mesurée par le daemon avec `measureWriterGeneration(hello.pid)`, la fonction qu'utilise le vérificateur. Le daemon mesure lui-même au lieu de croire `hello.pid_start`, pour que l'auteur et le lecteur comparent des valeurs de même source. L'écrivain est le daemon, la vie prouvée est celle du relais. `close("bye" | "socket")` supprime le snapshot ; `close("daemon_stop")` le garde (§7.1), comme un crash du daemon le laisse, valide puisque le relais vit et que le token est repris (§8.3).

**DÉCISION, mesure de l'heure de création d'un processus sous Windows par FFI.** `measureWriterGeneration` appelle `OpenProcess` (droit `PROCESS_QUERY_LIMITED_INFORMATION`), `GetProcessTimes` et `QueryFullProcessImageNameW` par `bun:ffi`, et met l'heure en forme identique octet pour octet au format `o` de PowerShell (`StartTime`) : l'auteur d'un snapshot écrit par l'une des deux formes reste lisible par l'autre, et la règle V du §8.4 compare des chaînes égales. Les échecs sont les mêmes (accès refusé, PID mort : `null`). `bun:ffi` est chargé à la demande, parce que le module est aussi empaqueté pour node (`server-deck.mjs`) : sous node la mesure journalise et rend `null`. Aucun PowerShell n'est lancé par la vérification du snapshot à chaque appel roadmap, par l'enregistrement de `server.ts`, ni par `mcp-daemon status` et `restart`. Écarté : garder PowerShell avec son délai de 5 s par mesure, qui faisait de chaque tempête de reconnexion N processus PowerShell et bloquait le balayage du broker. Écarté : faire écrire le snapshot par le relais, qui devrait alors connaître le token et le format du fichier.

**Reprise sans suppression (revue critique, point 2).** **DÉDUIT** `server.ts:1075-1081` : `writeGlobalCompanionIdentity` supprime le snapshot avant de mesurer la génération ; une mesure qui dépasse son délai laisse la roadmap en refus fermé avec une simple ligne de log. **DÉCISION** : sur une reprise par token acceptée avec le même PID de relais, le daemon ne supprime pas le snapshot. Il reprend `writer_generation` du ticket, sans mesure, et ne réécrit le fichier que si un champ d'identité a changé. Une première écriture mesure d'abord, et n'écrit qu'après une mesure réussie. Écarté : réécrire le snapshot à chaque reprise, ce qui rouvre la fenêtre de refus pendant la tempête de reconnexion.

### 8.3 Reprise après crash du daemon

1. Les relais voient la socket fermée, répondent l'erreur de coupure (§4.7) et se reconnectent ; le gagnant du verrou de lancement relance le daemon (§6.2).
2. Chaque relais peers présente son ticket dans le hello, avec `replay: true`.
3. Le daemon vérifie le ticket (§4.6). Ticket accepté, **du même groupe**, et broker annonçant `register_resume_version >= 1` : `/register` avec `resume_instance_token` et la `pid_generation` du ticket, signé par le credential de run s'il existe (tuile Kory), nu sinon (contrat §8.4). L'identité n'est gardée que si le broker répond `resumed: "token"`. Avec ticket du même groupe, le daemon ne supprime pas d'abord le fichier d'identité de tuile : les lecteurs (`server-deck.ts`, `desktop/mcp/deck-control-mcp.ts`, `desktop/hooks/desk-backchannel-hook.ts`) gardent un token valide pendant la coupure ; il le réécrit après l'enregistrement, et le supprime si l'enregistrement échoue pour de bon. Il garde aussi le snapshot global, réécrit seulement si un champ a changé (§8.2). Sans ticket, ou ticket d'un autre groupe, le comportement de démarrage ordinaire s'applique.
4. WS ouverte après l'enregistrement : le broker refuse une WS pour un token inactif, puis rejoue au plus 20 messages non livrés et les reprises de contexte. `notified_hwm` est figé à l'ouverture de la session et ne supprime que la re-poussée des messages poussés **avant** la coupure : ils restent lisibles par `check_messages`, car une poussée ne marque jamais `delivered`. Le dédoublonnage en cours de session reste `notifiedMessageIds` : un message plus ancien dont la poussée a échoué est repoussé plus tard.
5. Notice en channel, un seul message par ouverture : identité gardée (« claude-peers reconnected after a daemon restart; calls made during the outage failed; run check_messages ») ou identité changée (« ... you are now peer `<id>` »), regroupée par `notice_at` et `outages` du ticket (Q8). Le même texte va dans les logs.
6. Le relais roadmap se reconnecte sans ticket ; son prochain appel résout la session (§9).

Si Claude Code relance seulement le serveur MCP (`/mcp`), le nouveau relais n'a pas de ticket : chemin ordinaire, l'ancien PID de relais est mort, donc le broker ressuscite la ligne par `session_key` (`ARCHITECTURE.md`, « Resume flow »). Une tuile Kory garde en plus la reprise signée par le fichier d'identité. Si l'ancien relais vit encore, la règle S du §8.4 refuse la résurrection : la nouvelle session prend une identité neuve au lieu de voler celle d'un relais vivant.

### 8.4 Contrat d'interface pour la carte `1dc74e6c` (broker)

**Version annoncée.** `/health` expose `register_resume_version: 1`. Le daemon n'envoie une reprise nue que si cette version est présente ; sinon il enregistre par le chemin ordinaire et annonce l'identité changée. Un broker ancien ne voit donc jamais un champ qu'il refuserait (`admitRegisterAttestation` rendait 400 pour `resume_instance_token` sans `auth`).

**Requête.** `/register` accepte `resume_instance_token` sans `auth` pour une instance qui n'est **pas** liée à un run. Pour une instance liée, la preuve signée actuelle reste exigée (le bloc du candidat lié de `handleRegister`), puis les règles R2 à R4 s'ajoutent.

**Règles d'acceptation, toutes nécessaires :**

- **R1.** Le token désigne une ligne `peers` locale (`relay_id IS NULL`, `via IS NULL`), active ou dormante, du même `group_id` après la vérification TOFU, et du même `host`.
- **R2.** `body.pid` égale le `pid` enregistré, c'est-à-dire le PID du relais du dernier enregistrement. Si la ligne porte une génération (`pid_generation`, colonne optionnelle remplie à chaque `/register`), le corps en porte une égale : **un corps sans génération est refusé** (refus fermé, sinon omettre le champ sauterait la comparaison). Une ligne sans génération accepte toute valeur et la mémorise. Un `/register` sans `pid_generation` garde celle qui est stockée si le PID est inchangé et l'efface si le PID change. `pid_generation` est une chaîne de 256 caractères au plus, comparée à l'égalité par R2 ; le daemon l'envoie sous la forme `canonicalWriterGeneration` (`shared/relay-liveness.ts`), seule forme que la règle V sait confronter à une mesure ; un type faux, une chaîne vide ou trop longue donne un 400, jamais un champ ignoré (même règle pour `resume_instance_token`). `claude_cli_pid` n'entre pas dans la règle (§8.1).
- **R3.** Si `host` est l'hôte du broker, `body.pid` est vivant (`process.kill(pid, 0)` ; `EPERM` compte comme vivant, un PID qui n'est pas un entier positif jamais). Pour un broker distant, R1 et R2 suffisent : le token est le secret, et le broker ne sonde pas un PID étranger.
- **R4.** La clé `session_key` du corps n'est pas associée à un **autre** token qui tient la clé ; sinon l'association reste à ce token. Un autre token tient la clé si son PID est vivant sur l'hôte du broker (ligne active ou dormante), ou, pour un hôte que le broker ne sonde pas, si sa ligne est active. Conséquence : une ligne dormante sur un hôte non sondable perd la clé, et le B relancé sous un nouveau PID reçoit une instance neuve.

Aucune autre preuve n'est demandée, y compris hors Kory (Q4, DÉCIDÉ).

**Effet si accepté.** Mise à jour en place de la ligne, même si elle est active : pas de collision, pas de suffixe, `peer_id` et token conservés. Les champs de lancement (`cwd`, `role`, `desk_session`, `cc_session_id`, résumé) sont réécrits comme dans la branche de résurrection. `peer_sessions` est mis à jour sous R4. Réponse `resumed: "token"` ; le champ `resumed` n'existe dans la réponse que si la requête portait `resume_instance_token`.

**Deux règles hors de la reprise par token, exigées par la même carte :**

- **V, vivacité (Q9, DÉCIDÉ).** En `local` et `replica`, `sweepInactivePeers` ne rend pas dormant un pair local, même sans heartbeat, quand sa ligne porte une `pid_generation`, que son PID est vivant sur l'hôte du broker **et** que la génération mesurée de ce PID (`measureWriterGeneration`, mise en forme par `canonicalWriterGeneration`) égale la valeur enregistrée. Génération absente, différente (PID repris par un autre processus) ou non mesurable sur la plateforme : la règle des 120 s s'applique, donc une ligne de `server.ts`, qui n'en envoie pas, garde l'ancien comportement. Le balayage juge d'un seul bloc synchrone tout ce qui ne demande pas de mesure ; seules les lignes à mesurer attendent. Une seule sonde de PID, `pidExists`, sert `cleanStalePeers`, `peerIsLive`, le passage actif vers dormant de `/register` et les règles R3, R4, V et S : `EPERM` compte comme vivant, un PID qui n'est pas un entier positif jamais. En `remote`, rien ne change : 120 s sans heartbeat rendent le pair dormant. Le balayage tourne une passe à la fois : un tick qui tombe pendant une passe en cours est sauté et tracé (`guardedInterval`) ; la mesure est un appel FFI par ligne sous Windows (§8.2).
- **S, résurrection par `session_key` (revue critique, DÉDUIT de la branche de résurrection dormante de `handleRegister`).** Aujourd'hui, une ligne **dormante** trouvée par `session_key` est ressuscitée sans regarder son PID. Pendant une coupure longue, une nouvelle session du même dossier (par exemple en repli bun) prendrait le `peer_id` et le token du pair dormant, et le ticket du relais d'origine échouerait ensuite. **DÉCISION** : la résurrection par `session_key` refuse une ligne, même dormante, dont le PID enregistré est vivant sur l'hôte du broker **et différent de `body.pid`** ; elle suit alors la branche de collision (identité neuve suffixée, association inchangée). L'exemption `body.pid` égal au PID enregistré garde le chemin `switch_group` A vers B puis retour vers A : `server.ts` fait `/disconnect` sur l'ancien groupe puis se réenregistre avec le même PID, et reprend sa propre ligne. Écarté : compter sur V seule, car une ligne peut aussi devenir dormante par `/disconnect` ou en mode `remote`.

**Effet si refusé**, ou token inconnu parce que la ligne a été purgée : le champ est ignoré, le chemin ordinaire s'applique, la réponse porte `resumed: false` et le broker journalise le code de la règle en échec, jamais le token. Écarté : un 409 qui bloquerait l'enregistrement d'une session vivante pour un ticket périmé.

**Interactions :**

- **Époque de la capability de dépôt (Q3, DÉCIDÉ).** Conservée si la reprise par token est acceptée, avec le même PID de relais, et que `deposit_capability_hash` égale le condensat de la liaison en RAM. Sinon une nouvelle époque est mintée, comportement actuel. Raison : même relais et même capability veulent dire même lancement ; un crash d'infrastructure ne doit pas perdre le contexte que l'utilisateur a déposé avant `/clear`. Avec V, le propriétaire reste actif pendant la coupure en `local` et `replica`.
- **Snapshot de session.** Non invalidé par la même reprise (§8.2).
- **Tâches déléguées.** Liées au token (`ARCHITECTURE.md`, « Delegated tasks ») : token inchangé, rien à migrer, aucune tâche `orphaned`. Sans reprise, l'ancien token devient dormant puis supprimé, et ses tâches deviennent `orphaned` par la règle existante.
- **Fédération.** `relay_ref = sha256(token)` est inchangé : la réplique présente la même ligne au prochain passage. Avec V, une coupure du daemon ne rend plus la ligne dormante sur la réplique tant que le relais vit, donc le miroir amont reste actif. Aucune nouvelle règle de fédération.
- **Fichier d'identité de tuile.** Le token ne change pas : le fichier reste juste pendant la coupure et il est réécrit après la reprise (§8.3).
- **WebSocket.** La nouvelle authentification remplace l'entrée de `wsPool` (gestionnaire d'authentification WS) ; l'ancienne socket est déjà fermée avec le daemon mort.

**Deux candidats.** Deux relais ne peuvent pas présenter le même PID. Un processus du même utilisateur qui forgerait `pid` et token est hors du modèle de menace (§5) : il possède déjà ce token par le fichier d'identité.

## 9. Famille roadmap dans le daemon

**DÉCISION, clé de liaison des deux relais d'une session :** `(sha256(CLAUDE_CODE_MESSAGING_SOCKET), ppid, ppid_start)`. Le socket de messagerie est la clé du snapshot actuel (`server-roadmap.ts`). Le PID et l'heure de création de `claude.exe` empêchent qu'une valeur de socket héritée par un autre processus relie deux sessions différentes. **Un `ppid_start` vide (heure non mesurable) ne donne aucune liaison** : la roadmap reste sur le chemin du snapshot, plutôt que de lier sur une clé affaiblie. Écarté : le socket seul, qu'un `claude` imbriqué héritant de l'environnement d'une tuile pourrait présenter ; aussi `CLAUDE_CODE_SESSION_ID` seul, qui change à `/clear` ; aussi lier sur `(socket, ppid)` quand l'heure manque.

L'index vit dans `shared/mcp-daemon-links.ts` ; `shared/mcp-daemon-families.ts` construit les deux familles autour d'un seul index (module séparé : si `links.ts` importait les familles, il y aurait un cycle d'import). Une session peers entre dans l'index une fois enregistrée et en sort au début de sa fermeture.

**Résolution, à chaque appel d'outil** (la session peers peut changer de groupe, de nom ou d'enregistrement entre deux appels) :

1. L'index de liaison donne les sessions peers **ouvertes et enregistrées** ayant la même clé. Les sessions en fermeture sont exclues. Une session dont `identity()` est nul est exclue aussi : `identity()` est nul pendant un changement d'identité (`switch_group`, `set_id`) et après un changement échoué, le drapeau étant baissé de façon synchrone quand le snapshot global est invalidé et levé quand il est écrit. Une session en plein `switch_group` n'est donc pas candidate, et un appel roadmap lié n'écrit jamais au nom du pair dormant de l'ancien groupe.
2. **Exactement une** : son identité en mémoire (peer, token, `projectKey`, URL canonique du broker). L'URL du broker résolue depuis le hello roadmap doit égaler celle de la session peers, sinon refus, comme le contrôle actuel (`server-roadmap.ts`). Aucune mesure de processus.
3. **Aucune** : lecture du snapshot avec vérification de la génération d'auteur, comme aujourd'hui. Ce chemin couvre une session dont la famille peers tourne sur `server.ts` en repli, et tout le lot L2.
4. **Deux ou plus** : refus « Roadmap companion identity is ambiguous », journalisé avec les deux `session_id`. Jamais la première ou la plus récente.
5. Sans socket de messagerie : refus, comme aujourd'hui.

Les refus gardent le texte actuel « Roadmap companion identity is unavailable » pour 2 et 3, avant tout trafic vers le broker.

## 10. Repli et configuration

**Configuration globale de Claude Code**, deux formes par famille :

```json
"claude-peers":  { "command": "<root>/bin/<plateforme>/claude-peers-relay[.exe]", "args": ["--family", "peers",   "--fallback", "<root>/server.ts"] },
"kory-roadmap":  { "command": "<root>/bin/<plateforme>/claude-peers-relay[.exe]", "args": ["--family", "roadmap", "--fallback", "<root>/server-roadmap.ts"] }
```

`<plateforme>` vaut `${process.platform}-${process.arch}` (par exemple `win32-x64`, `linux-x64`, `darwin-arm64`). Avant la v1.0, aucune CI ne produit le binaire et il n'est jamais commité : `bun scripts/relay-setup.ts` le construit pour l'hôte (cible `x86_64-unknown-linux-musl` sous Linux), l'installe à cet emplacement et affiche les deux commandes `claude mcp add` ; sans cargo ou en cas d'échec de la construction, il affiche la forme bun, sauf si un binaire est déjà installé (forme relais avec ce binaire). Le script n'écrit jamais la configuration de Claude Code (pas d'installateur dans `cli.ts`, `docs/DESIGN-MCP-FAMILIES.md` §4).

Forme bun, inchangée : `"command": "bun", "args": ["<root>/server.ts"]`. Option `--bun <chemin>` du relais : interpréteur pour le daemon et le repli, `bun` du `PATH` par défaut. Le daemon est cherché à côté du fallback : `<dossier du fallback>/mcp-daemon.ts`.

**Choix du repli, en deux temps :**

- **À l'installation.** Binaire présent pour la plateforme : forme relais ; sinon forme bun. Commandes `claude mcp add` documentées dans `README.md`. Pas d'installateur dans `cli.ts`, conformément à `docs/DESIGN-MCP-FAMILIES.md` §4. Un binaire supprimé après l'installation fait échouer le serveur MCP de façon visible ; ce cas n'est pas rattrapé.
- **Au démarrage d'une session, dans le relais.** Si aucune session ne s'ouvre auprès du daemon dans les 10 s (aucun candidat ne porte un daemon de sa racine après le lancement, tous les candidats occupés sans daemon valide, version refusée après `AUTH_OK`, `family_unavailable`, `session_limit`, `hello_invalid`, clé illisible ou aux droits trop larges), le relais lance `bun <fallback>` avec son propre environnement et son cwd. Il n'a lu aucun octet de stdin avant ce moment (la lecture ne commence qu'après `WELCOME`) : le premier `initialize` de Claude attend dans le tube, et le repli hérite des descripteurs d'origine, sans copie ni tampon à rejouer. Sous POSIX le relais remplace son image par `exec`. Sous Windows il reste parent, attend la fin de bun et sort avec son code ; `claude_cli_pid` vaut alors le PID du relais, sans conséquence puisque rien ne le lit (§8.1). Écarté : une variable dédiée pour corriger un champ sans lecteur. Le relais en repli écrit sa cause dans `<home>/.claude/peers/mcp-fallback-<pid>.json` (`pid`, `pid_start`, `family`, `cause`, `fallback`, `started_at`), supprimé à sa sortie sous Windows et ignoré si le PID est mort (sous POSIX l'`exec` empêche de le supprimer) : `bun cli.ts mcp-daemon status` liste ainsi les sessions en repli (Q5, DÉCIDÉ). **Exigence côté daemon (L2)** : `status` ignore une entrée `mcp-fallback-<pid>.json` dont le PID est mort **ou** dont le `pid_start` ne correspond plus à l'heure de création de ce PID (PID réutilisé) ; le relais ne nettoie pas ces fichiers sous POSIX. Sans cela, un repli permanent reste invisible. **Pas de repli au milieu d'une session** : après une première ouverture réussie, le relais se reconnecte seulement au daemon. Un serveur bun lancé en cours de session s'enregistrerait avec un autre PID et prendrait une identité suffixée. Écarté : relais sans repli, où un daemon défaillant rend toutes les sessions muettes.

**Effet sur L2.** `family_unavailable` permet d'installer les deux relais dès L2 : tant que le daemon ne sert que la roadmap, le relais peers passe en repli sur `server.ts`, qui écrit le snapshot que lit la roadmap du daemon.

**Tuiles Kory hôte.** Elles utilisent la configuration globale de l'utilisateur ; Kory n'écrit pas de configuration MCP pour elles. `demo-driver.ts` copie les entrées globales telles quelles : chemins absolus requis.

**Lancement du broker par le Deck (revue critique, point 4).** **DÉDUIT** `desktop/src/main/broker-spawn.ts:57-70` : le Deck lance le broker avec la `command` de l'entrée MCP `claude-peers`. Avec le relais configuré, il lancerait le relais sur `broker.ts`. **DÉCISION, en L2** : `locateBrokerScript` trouve toujours l'argument qui finit par `server.ts` (la valeur de `--fallback`) ; quand la commande est le relais, il lance le broker avec la valeur de `--bun`, sinon `bun`. Un test du module existant le couvre. Écarté : une entrée de configuration dédiée au broker, qui ajoute une source de vérité de plus.

**Job des tuiles Kory (Q10, DÉCIDÉ, §6.1).** En L2, `JOB_PREAMBLE_PS` (`desktop/src/main/shell-command.ts`) passe aux limites `0x2800` (`KILL_ON_JOB_CLOSE | BREAKAWAY_OK`).

**Tuiles sandbox.** Inchangées : enregistrement `claude mcp add` dans le volume du conteneur, sur `bun server.ts` et `bun server-roadmap.ts`. Le cwd, les PID et l'hôte d'un conteneur n'ont pas de sens pour un daemon hôte (couplage 15).

## 11. Modes du broker

| Mode | Ce qui change pour le daemon |
|---|---|
| `local` | Le daemon peut lancer le broker pour une URL de loopback, en vol unique par origine canonique du broker (`shared/broker-ensure.ts`). Le processus broker est lancé avec l'env du daemon recouvert par les variables de broker du hello de la session déclenchante (`CLAUDE_PEERS_PORT`, `CLAUDE_PEERS_DB`, `CLAUDE_PEERS_BIND_HOST`, `CLAUDE_PEERS_BROKER_TOKEN`, `CLAUDE_PEERS_OFFLINE_REPLICA`, `CLAUDE_PEERS_SERVE_REPLICAS`, `CLAUDE_PEERS_DELEGATION_*`), comme `server.ts` donne le sien, et avec le vrai binaire bun, jamais la copie `kory-mcp-daemon`. Une session qui rejoint un vol lancé avec d'autres réglages de broker est journalisée par son nom. Seul « aucune réponse de `/health` après N tentatives » est réessayable (§7.1) ; un refus du marqueur d'arrêt ne l'est pas. Le broker sonde le PID du relais ; un relais vivant garde le pair actif (règle V). |
| `replica` | Comme `local` pour le daemon : les clients parlent au broker de loopback, règle V comprise. `relay_ref` est stable par la reprise. Les approbations et la boîte opérateur restent sur le broker local. |
| `remote` | Jamais de lancement de broker (refus actuel d'une URL qui n'est pas de loopback). **DÉCISION** : le daemon sonde `/health` du broker distant, et un broker injoignable est **réessayable** : la session reste servie et réessaie l'enregistrement (§7.1) au lieu d'échouer. Écarté : traiter le distant injoignable comme fatal, ce qui coupe toutes les sessions d'un poste dont le broker est derrière un réseau lent. Le broker ne sonde pas les PID : vivacité par heartbeat, limite de 120 s maintenue, reprise par R1 et R2 sans R3, règles V et S sans effet. Le Bearer vient de la session. Clé du daemon, snapshots et fichiers d'identité restent locaux, ce qui justifie le daemon local plutôt qu'une route du broker. |

**DÉCISION, le marqueur d'arrêt interdit de LANCER, pas d'UTILISER.** Le marqueur d'arrêt manuel du broker fait rejeter un lancement, avec le chemin du marqueur et sa date dans l'erreur. Une session qui rejoint le lancement d'une autre session relit son propre marqueur quand son fichier de réglages diffère ; mais si le lancement a réussi et laissé un broker vivant, elle l'utilise : le marqueur n'a jamais empêché une session de parler à un broker déjà en vie, sur le chemin stdio non plus. Écarté : refuser aussi l'usage, ce qui rendrait muette une session à cause d'un broker qu'une autre a légitimement lancé.

**Broker lancé détaché (revue critique, point 3).** **DÉDUIT** `server.ts:315-318` : le lancement actuel n'est pas détaché. **MESURÉ le 2026-11-08** (Windows) : un enfant bun lancé sans `detached` meurt avec son parent, dans le job du shell ; avec `detached: true`, `windowsHide: true`, stdio ignoré et `unref()` il survit, sans fenêtre de console. Un arrêt du daemon arrêterait donc le broker attaché, ses dépôts en RAM et ses WebSocket. **DÉCISION** : le daemon lance le broker détaché (`node:child_process.spawn` avec ces quatre réglages). Écarté : garder le lancement attaché, qui lie la vie du broker partagé à celle du daemon. Le lancement se fait par `node:child_process.spawn` avec ces quatre réglages, par le lanceur de `shared/broker-ensure.ts` que `mcp-daemon.ts` construit et passe aux familles par `ctx.brokers`. Sous Windows, `Bun.spawn` réinjecte le `USERNAME` du parent dans l'env de l'enfant : aucun test ne l'affirme.

**Clés.** L'endpoint d'une session est résolu depuis son hello et le fichier de réglages : deux sessions peuvent viser deux brokers. Aucune table du daemon n'est indexée par groupe ou par broker seul. Le registre est indexé par `session_id`, minté par connexion.

## 12. Stratégie de test par lot

Règles : `CLAUDE.md`, « Rules for tests ». Chaque test nomme la mutation de la source qui le fait tomber. Le daemon se démarre **en processus** par `startDaemon({ port: 0, keyPath, logDir, idleSec, pollFallbackMs })`, une fois par fichier dans `beforeAll`, avec un faux relais TypeScript qui parle les trames. Un « crash » est `stop()` puis un nouveau `startDaemon` sur le même port. Aucune attente sur le temps réel : horloge injectée, ou intervalle au plancher et attente de la **condition**, bornée.

## 13. Questions pour l'opérateur

| # | Question | Recommandation |

| Q1 | Port dérivé par utilisateur OS plutôt qu'un port fixe ? | **DÉCIDÉ par l'opérateur le 2026-11-06 : oui, avec 10 ports candidats.** Le port dérivé (§4.1) puis les 9 suivants. Le daemon écoute sur le premier libre ; le relais les essaie dans l'ordre et s'arrête au premier qui passe l'authentification mutuelle (§5). Un port occupé par un autre programme ou par le daemon d'un autre compte est sauté au lieu de forcer le repli. Le port reste le verrou : un daemon par port. Même règle sur Windows, Linux et macOS. | Q4 | Accepter une reprise nue par token et PID pour les sessions hors Kory ? | **DÉCIDÉ par l'opérateur le 2026-11-06 : oui.** Le token est déjà un secret porteur écrit dans le fichier d'identité ; R2 ajoute la preuve du processus. Sans cela, chaque crash du daemon suffixe les sessions hors Kory. |
| Q5 | Repli bun au démarrage quand le daemon ne s'ouvre pas ? | **DÉCIDÉ par l'opérateur le 2026-11-06 : oui, au démarrage seulement**, plus une visibilité : `bun cli.ts mcp-daemon status` liste les sessions en repli (chaque relais en repli l'inscrit, avec sa cause, dans un fichier d'état par PID sous `<home>/.claude/peers/`, retiré à sa sortie et ignoré si le PID est mort). Sans cela, un repli permanent reste invisible. |
| Q6 | Lancement par WMI si le job object de Claude Code tue le daemon ? | **Sans objet** depuis les mesures du 2026-11-06 (§6.1) : hors Kory, l'enfant d'un serveur MCP survit à la session ; dans une tuile Kory, `BREAKAWAY_OK` (Q10) suffit. |
| Q7 | Redémarrage pour mise à jour : CLI seule, ou aussi un bouton du Deck ? | **DÉCIDÉ par l'opérateur le 2026-11-06 : CLI seule**, et la procédure de mise à jour documentée dans `README.md` (`bun cli.ts mcp-daemon restart` après le déploiement). | Q8 | La notice de reconnexion en channel à chaque reprise : acceptable comme bruit ? | **DÉCIDÉ par l'opérateur le 2026-11-06 : oui, sans jamais répéter.** Une seule notice par reprise, poussée une fois par le relais peers à la reconnexion ; jamais jointe aux réponses d'outils ni répétée à chaque appel. Plusieurs reprises proches (daemon qui redémarre en boucle) sont regroupées : au plus une notice par session toutes les 10 minutes, qui donne le nombre de coupures depuis la précédente. Le relais roadmap n'en envoie pas : il n'est pas un channel. |
| Q9 | Un dépôt de contexte est perdu quand le pair passe dormant, après 120 s de coupure du daemon sans heartbeat. Exigence ajoutée à la carte `1dc74e6c`. Vaut pour les modes `local` et `replica` (même hôte) ; en `remote`, le broker ne peut pas sonder le PID et la limite de 120 s demeure. Règle V du §8.4. |

| Q11 | Deux clones du dépôt utilisés en même temps : un daemon par racine de code (sur deux des 10 candidats), ou un seul daemon et le repli bun pour l'autre clone ? | **DÉCIDÉ par l'opérateur le 2026-11-06 : un daemon par racine** (§4.4). Contexte de l'opérateur : le clone `koryphaios-mcp` sert les sessions pendant le développement de Kory ; ce n'est pas la cible d'un utilisateur. Pendant le développement du daemon, les sessions de travail restent sur les serveurs bun ; seules des sessions de test pointent vers le relais par `--mcp-config`. La configuration globale et `koryphaios-mcp` passent au daemon une fois la version stable (L6). Avec un seul daemon, une session dont le daemon a été relancé par un relais de l'autre clone ne peut plus se reconnecter, faute de repli en cours de session. Coût : un daemon de plus, seulement quand deux clones servent des sessions en même temps. |

## 14. Écarts et précisions par rapport au plan par lots

Le plan `docs/DESIGN-MCP-DAEMON-LOTS.md` a été aligné sur ce document le 2026-11-06. Restent ces précisions de fond :

- « Son port d'écoute sert de verrou d'instance unique » : conservé, sur 10 candidats par utilisateur OS, un daemon par port, le plus bas gagne par racine de code (§4.1, §6.2). Un port unique bloque le second compte d'une machine et, sans authentification mutuelle, livre les secrets de groupe à quiconque l'occupe en premier.
- « Le relais devient aussi l'auteur du snapshot » : précisé. Le daemon écrit ; la génération prouvée est celle du relais (§8.2).
- « Le broker reçoit le PID du relais (et de son parent `claude.exe`) » : le PID de `claude.exe` est envoyé mais n'est une preuve de rien, faute de lecteur (§8.1).
- « Répond aux appels par une erreur explicite » : précisé pour les requêtes en vol, dont l'exécution est inconnue (§4.7).
- « Démarre le daemon s'il est absent » : confirmé hors Kory ; dans une tuile Kory, exige `BREAKAWAY_OK` dans le job de la tuile (§6.1, Q10), livré en L2 avec la correction de `broker-spawn.ts`.
- Estimation de L4 : l'inventaire confirme 3 à 4 jours **si** L4 comprend la conversion des helpers du §7.3 et de leurs appelants hors cœur. Ajouter 0,5 jour pour le passage de `server.ts` en entrée mince et le déplacement des exports de `server-deck.ts` (groupe R). L1 et L2 gagnent chacun environ 0,5 jour (candidats, verrou de lancement, daemon bloqué, nom de processus ; job des tuiles, `broker-spawn.ts`, broker détaché), L3 jusqu'à 0,5 jour pour les règles V et S. Total du plan : 10,5 à 13,5 jours. **SUPPOSÉ**, estimation.
